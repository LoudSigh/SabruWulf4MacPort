# Sabre Wulf native-port workbench

**Chosen direction: faithful 1984 gameplay with modern native presentation. Current result: a rights-safe prototype, not the completed port.** The three SwiftUI targets build as separate macOS, iOS and visionOS apps and share a deterministic `GameCore`. The four-room maze, icons, interactions and timing are independently authored placeholders. The original 16×16 layout and room-template *structure* have now been validated privately, but original room/art bytes are not bundled; the complete game code, audio, rules and winning conditions have **not** been reconstructed in these apps. [Spec.md](Spec.md) distinguishes the behavior that must be preserved from presentation that may change.

## Get started

1. **Want to see something now?** Double-click [Run Sabre Wulf Preview.command](./Run%20Sabre%20Wulf%20Preview.command) on this Mac, or run `./Run\ Sabre\ Wulf\ Preview.command` from the repository root. It opens the native app with **placeholder gameplay plus a separate partial original-movement preview**, the original static menu/gameplay captures in Preview and a private 16×16 room-type map in your browser. [Exact instructions](docs/run-preview.md) explain what you can and cannot interact with. No original content is added to the app or Git.
2. Open this repository in VS Code with the recommended [extensions](.vscode/extensions.json). Xcode and its SDKs are required to build Apple app bundles; [build instructions](docs/build.md) include `xcodegen generate`, `swift test` and three `xcodebuild` schemes.
3. Read [Spec.md](Spec.md) for evidence gates and [COPILOT_PROMPT.md](COPILOT_PROMPT.md) for the VS Code Autopilot execution prompt. The prompt expects verified results, not a claim of completion based on this prototype.
4. Keep the user-supplied TZX, snapshots, AY tune and Spectrum ROM outside the repository. Their hashes, format metadata and unresolved edition/rights status are listed in the [input manifest](reverse_engineering/input-manifest.json). The [menu baseline](reverse_engineering/analysis/menu-reference.json), [in-game baseline](reverse_engineering/analysis/gameplay-reference.json) and [initial RAM map](reverse_engineering/analysis/memory-map.md) enable static comparison. The [tape investigation](docs/tape-analysis.md) gives a repeatable, metadata-only snapshot comparison command and explains why continuous gameplay replay remains unverified.
5. Follow the [release QA plan](docs/qa-plan.md). Public CI uses only synthetic tape fixtures and original placeholder UI; no source game media is uploaded.

For local-only source recovery, use the [private snapshot analysis workflow](docs/local-reverse-engineering.md). It records bounded executable-address/write metadata and can generate RAM/disassembly **only in ignored private paths**; its exploratory trace is not a complete game implementation.

The user-supplied [SkoolKit reference cross-check](docs/external-reference.md) now confirms a 16×16 room layout, 48 reusable room templates and their bounded RAM range against **both** local snapshots. Its optional private world-map viewer is structural, not original game artwork; the native prototype remains a separate 2×2 placeholder.

The same source-backed analysis has validated a 196-entry sprite pointer table and 153 bounded sprite records in both snapshots. A generic 1-bit [SpriteMask decoder](Sources/GameCore/SpriteMask.swift) reproduced the silhouettes of two privately compared frames; original image data remains private. The native apps can [import the private 16×16 world reference](docs/build.md) for exploration of all 256 positions, measured background bounds and recorded actor replays. A separate, **partial** source-backed movement preview applies the captured player's inertia and static background collision, including one validated northward room crossing and return. Its room/X/Y matched 980 bounded source checkpoints. Reference-relative CPU stepping now matches the unmodified emulator's **entire 48K RAM on every frame** of the checked 180-frame north exit, 200-frame round trip and 256-frame west schedule; the former RNG/enemy disagreement was caused by absolute frame-boundary drift. West/east passages in the *native* static-only preview remain provisional: it does not model the reference's enemy encounters and damage. An optional private viewer compares recorded enemy positions; it is **not** native enemy AI. The main interactive four-room placeholder remains separate and must not be mistaken for the historical game.

A private, reference-timed 100-frame T-key replay also verifies every RAM/screen hash and exposes numeric player-state changes in the viewer. It is a **recorded fire observation**, not implemented combat; the native movement slice continues to reject fire until hit detection and outcomes are recovered.
Three 190-frame private runs—with T, without T and with an unrelated A-key timing control—reproduce every RAM/screen hash. Source write/RNG tracing now explains the first T-specific enemy direction change at frame 156: T had shifted RNG by frame 146, changing the result of a random-direction branch. A also shifts RNG and encounter timing. T avoids the control runs' damage through frame 190, but this does **not** establish a sword hit, enemy damage or an implemented native attack rule.
A pure [source contact predicate](Sources/GameCore/CapturedActorContact.swift) now matches **3,881/3,881** routine results in six paths with **1,206/1,206 complete RAM-frame matches**. Its positive contacts precede the recorded damage-state changes, so autonomous enemies, hit consequences and life loss remain unimplemented. [Numeric evidence](reverse_engineering/analysis/reference-contact.json) excludes private RAM or disassembly.
A [bounded enemy-motion step](Sources/GameCore/CapturedEntityMotion.swift) matches **17/17** source X/Y updates when supplied observed velocities, using static room collision. A separate [direction chooser](Sources/GameCore/CapturedEnemyDirection.swift) implements all eight source velocity choices from **supplied** RNG/clock bytes and matches four source decisions. Neither rule generates the refresh-register RNG, schedules actor updates or creates autonomous native enemies.
A separate [bounded active-enemy state](Sources/GameCore/CapturedActiveEnemyState.swift) matches 14/14 slot-12 kind/position changes and three countdown-only frames across three reference-timed paths. Countdown and movement can fall in adjacent displayed frames; the caller must supply those events. This does not implement enemy scheduling, timer expiry, contact-driven injury or autonomous combat.
A [source-backed expiry decision](Sources/GameCore/CapturedEnemyExpiry.swift) matches both observed timer-1 branch outcomes in a 250-frame encounter when supplied the source RNG and clock bytes: a moving enemy pauses and reseeds its timer, while a stopped one chooses a new direction. This remains a bounded, externally triggered rule—not a native RNG, actor scheduler, or complete combat loop.
The active-enemy state now composes those supplied events across **74 consecutive source-checked frame ends** after the T-path direction choice, including one countdown that precedes its final movement and an observed timer wrap from 0 to 255 to 254. It still needs externally supplied event timing and randomness.
The two [source RNG arithmetic steps](Sources/GameCore/CapturedRNGStep.swift) match 8,740/8,740 writes in reference-relative private checks with the reference CPU's refresh, carry, counter and clock values supplied. The native port still cannot generate the instruction-path-dependent refresh input or update cadence.
Three 600-frame T/no-T/A follow-ups also match every reference RAM/screen hash and **4,477/4,477** source contact returns. The first injury shows 66 frames of actor kind 65 before the source life byte falls 1→0; T eventually takes a contact at frame 228. The native viewer can scrub the long private no-fire replay and display the life byte, but these traces do not establish the general damage or ending rules.
The first kind-65 countdown is now a narrow shared core operation checked against **189/189 source actor-update transitions**. It is not a per-display-frame timer: 63 actor updates occupy 66 visible frames here. Native enemy contact, injury triggering and game-over progression remain unwired.
Three private 800-frame continuations establish the **visible** return to the captured menu's center text at frames 503, 510 and 679 under no-T/A/T controls, with **2,400/2,400** independent RAM/screen hashes verified. The [numeric gate](reverse_engineering/analysis/reference-menu-return.json) does not certify the full menu or implement new-game/endgame logic.
The `0` key has also restarted the no-T reference path: [source-free checkpoints](reverse_engineering/analysis/reference-restart.json) show room 168, X=120/Y=112 and life byte 4 stabilizing by frame 660, with **29,056/29,056** covered source background RGB pixels by frame 664 and **800/800** RAM/screen hashes matching the emulator. The native app can inspect that private replay but does not yet initialize a playable original-game start.
A [keyboard-selected long-W reference](reverse_engineering/analysis/reference-restart-keyboard.json) also moves the newly restarted actor from X=120 at frame 788 to X=148 at 800, with **800/800** RAM/screen and **29,056/29,056** covered static room pixels verified. The **full** native menu/startup and movement rules remain unimplemented.
Four [post-setup direction paths](reverse_engineering/analysis/reference-new-game-movement.json) provide a **second partial native movement origin**. Shared Swift state matches **110/110** source room/X/Y **and sprite ID** frames 791–900 for each Q/W/E then None schedule; R is limited to **76/76** through frame 866, before an unexplained next-frame difference. Menu startup timing, enemies, general mixed controls and a complete native new game remain unported.
A [single measured W→E change](reverse_engineering/analysis/reference-new-game-mixed.json) also matches **110/110** room/X/Y frames after setup; its bitmap ID is checked for **76** frames and hidden thereafter. This does not generalize to arbitrary mixed controls, enemies or complete gameplay.

The preview launcher can export a **private 196-ID sprite atlas** from the two matching snapshots. The app decodes 152 nonempty bitmap shapes and displays user-selected masks as newly drawn 1-bit silhouettes; the original bytes remain ignored. This does not establish original color, animation order or redistributable art.
Five independently replayed 100-frame Q/W/E/R/T runs establish the captured player's screen placement: sprite rows are displayed bottom-up, source X is the left edge and source Y the bottom row. The private verifier agrees on **489/500 full player rectangles** (**173,348/173,472 pixels**); 124 mismatches in 11 W frames have not yet been attributed to a specific drawing rule. The native viewer can overlay the locally imported recorded silhouette in the room, but still has no general actor-layer compositor or native attack logic.

A second ignored atlas recovers **41 distinct background bitmaps** and their attribute-grid structure from the supplied snapshots, covering all 919 imported placements. The native explorer can draw recovered monochrome shapes without downloaded PNGs, with an optional **approximate 48K ink/paper color preview**. FLASH timing, transparency and whole-room compositing remain unverified. This is inspectable progress toward faithful presentation, not completed gameplay or a distributable original-art build.
Direct placement and bitmap-bit inversion now match **29,056/29,056**, **28,544/28,544** and **30,720/30,720 covered RGB pixels** in the captured, north-exit and west-exit rooms, respectively. The shared `BackgroundScene` compositor used for these checks also prepares in-memory, transparent color overlays for all 48 room templates in the native viewer after a local import. Private rendered frames correct the keyboard labels to **E up / R down**; previous bottom-origin rendering was wrong. These three static template matches do not establish dynamic sprites, uncovered pixels, native display scaling or complete scene fidelity.
Those 41 records are contiguous from `0x70BC` through `0x9691`; the [RAM coverage inventory](reverse_engineering/analysis/byte-coverage.json) now classifies **29,178/49,152 bytes** as data and keeps **19,974** unknown, rather than misidentifying graphics as executable code.
Across eight fully RAM-verified replay paths, an offline [executed-PC inventory](reverse_engineering/analysis/executed-pc-coverage.json) identifies **2,589 distinct RAM entry addresses** with no overlaps against known world/graphic/sprite data. This is not a whole-program disassembly or an excuse to relabel all unknown RAM as code; detailed address lists remain private.
The version-2 [private world import](docs/build.md) now checks four reconstructed source hashes, including every placement's measured bitmap bounds. Editing a room's gameplay geometry is rejected instead of masquerading as the captured game; modern presentation can still change independently.
