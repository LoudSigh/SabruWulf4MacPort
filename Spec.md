## 1. Outcome and boundaries

Analyze the user-supplied ZX Spectrum 48K edition of Ultimate's *Sabre Wulf*: recover its loaded program, code/data boundaries, graphics, room data, audio behavior, rules, and observable interactions. Deliver independently launchable, native macOS, iOS, and visionOS apps implemented in Swift. The playable port must implement the recovered behavior, not embed a Spectrum emulator as its game runtime. Use the emulator only as a reference, test oracle, and analysis tool.

### Product direction: faithful game, modern presentation

The user chose a **faithful port with modern presentation**, not a reinterpretation. Preserve the verified 16×16 world topology and room templates, game state transitions, movement/collision outcomes, enemies, attack, inventory, lives, scoring, progression, ending, and timing relationships. Do not replace these with the prototype's four-room maze or invent missing behavior. Treat every intentional deviation from measured original behavior as a separately documented, opt-in setting; do not silently change the default game rules.

Modernize the presentation layer: native windows and menus, high-resolution scaling, optional newly authored visual treatments, accessible text and controls, platform-appropriate keyboard/controller/touch/spatial input, audio output, and pause/resume. Map each platform's controls onto the **same** game actions; display size, device frame rate, and art theme must not change the simulation state produced by a given input replay. Provide an original-style visual reference mode for comparison when authorized assets are available. The optional supplied AY tune is an explicitly labeled alternative soundtrack, never evidence of original 48K audio.

For the 1-player Spectrum keyboard option, measured private frames establish Q=left, W=right, **E=up, R=down**, T=fire. An earlier external-direction label for E/R was reversed: E moves the rendered player toward smaller screen Y and R toward larger screen Y. The keyboard-row routine at address 45306 was privately matched to the captured RAM; controlled Q/W/E/R/T replays and a W/E room crossing validate selected actor positions. Implement those **actions** once in `GameCore`; adapt native arrows, controllers, touch and visionOS input onto the actions rather than tying simulation to physical keys. Bounded source replays do not validate every movement distance, collision, combat or room transition in the native game. The current prototype's arrow/WASD mappings remain unrelated placeholders.

Keep `GameCore` deterministic and independent of SwiftUI/Metal and the reference emulator. Keep original media, extracted art, disassembly and source RAM only in ignored private storage; public builds must use original newly authored placeholders or a rights-cleared local asset-import path. A source-backed core with substitute art can be called a **behavioral port**, but not a visually faithful release until the permitted original-style presentation has been validated. The existing prototype is neither.

Its empty remote was bootstrapped from this working directory on `main` with the spec and prompt; verify Git state and the remote branch before subsequent work. Never overwrite the emulator backup or assume future changes have been pushed. Keep private source media and extracted game content out of public commits unless redistribution rights have been confirmed.

Rights are **not** established by the existence of files or this spec. Record provenance and permitted uses of each supplied file before copying, publishing, or bundling it. **The user explicitly forbids storing disassembly on GitHub. Never stage, commit or push original instruction bytes, mnemonics, annotated listings, raw RAM dumps or recovered game assets regardless of licensing; keep these only in ignored local `reverse_engineering/private/` or `reverse_engineering/generated/`.** Public files may contain hashes, numeric addresses, counts, schemas, tool source and high-level behavioral findings that do not reproduce original code/art. ## 4. Phases, artifacts and exit gates

Execute in dependency order. Maintain a small task list showing evidence, owner, status, next action and blockers. At each gate, run the smallest relevant test and record commands/results. Do not silently substitute stubs for a required input.

1. Inventory this workspace, the supplied game files and the read-only emulator; check repository state, toolchain and disk paths. Compare existing filenames/hashes before treating them as canonical. Verify source-control/redistribution rules and create `.gitignore` first.

### Phase B: reconstruct loaded program and data

1. Parse each tape block with offsets, checksums, header type, BASIC loader instructions, CODE start/length, concatenation and entry point. Separate loader/ROM effects from program bytes. For TZX, handle only evidenced block types and fail explicitly on unsupported blocks. Prefer snapshot-derived memory only after validating it against a known run.
2. Identify self-decompression, relocation, RAM overlays, writable code/data and interrupt modes. Log memory intervals with initial vs post-load hashes and provenance; a byte not yet classified remains `unknown`, not presumed instruction.
3. Produce a 64 KiB 48K memory map with ROM/RAM boundaries, disjoint program/data regions, screen bitmap/attribute regions, stack, variables and write hotspots. Build reachable Z80 disassembly from validated entry points and trace targets; classify code, data, graphics, tables and uncertain bytes. Track jump tables, indirect calls, subroutine inputs/outputs, interrupt behavior, state machines and cross references.
