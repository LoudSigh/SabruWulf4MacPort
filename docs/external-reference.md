# Sabre Wulf reference cross-check

The user pointed to [ArcadeGeek's SkoolKit Sabre Wulf index](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/), labeled there as a **work-in-progress** RAM disassembly. Useful navigable references include its [data map](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/maps/data.html), [routines map](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/maps/routines.html), [backgrounds](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/graphics/backgrounds.html), [graphics index](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/graphics/graphics.html), [game-state buffer](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/buffers/gbuffer.html) and [credits](https://skoolkit.arcadegeek.co.uk/ultimate/sabrewulf/dec/reference/credits.html).

**Copyright boundary:** the pages credit Ultimate Play the Game and ArcadeGeek; the linked upstream repository reports no explicit reuse license. These pages are pointers for analysis, **not** permission to copy their disassembly, graphics, rendered room images or game data into this repository. The user additionally requires **no disassembly on GitHub**. Keep all source bytes, local listings and derived original layouts/images inside ignored `reverse_engineering/private/` only. Public analysis here contains numeric addresses, counts, hashes and independently worded conclusions.

The source-backed ranges `0x6066–0x70BB`, sprite pointer table `0xBF84–0xC10B`, and its bounded sprite records can now be treated as data in [byte-coverage.json](../reverse_engineering/analysis/byte-coverage.json). Screen bitmap/attributes are also known, totaling **19,492 classified data bytes** of 49,152 RAM bytes. The remaining 29,660 are still marked `unknown`; diagnostic instruction-start addresses do not by themselves classify instruction lengths. [room-index.json](../reverse_engineering/analysis/room-index.json) and [sprite-index.json](../reverse_engineering/analysis/sprite-index.json) record aggregate counts and input hashes without publishing original layout, images or instruction bytes.

Two independently recovered Sabreman bitmap records (sprite IDs 16 and 21) were compared **privately** to the site's locally downloaded sample images. The simple 1-bit MSB-first bitmap shape matches their nonblack pixels exactly (336/336 and 352/352) after accounting for the image reader's vertical coordinate direction. A generic [SpriteMask decoder](../Sources/GameCore/SpriteMask.swift) and synthetic unit tests are in the shared Swift package; no bitmap payload or source PNG is in Git. The check does not validate the full sprite catalogue or original display attributes.

## Reproduce and inspect privately

Run from the repository root. This tool uses the locally installed Carbon Neural emulator's `SpeccyCore` parser without copying its source here:

```sh
SPECCY_CORE_DIR='/Volumes/July2025inclOct2022/Visual Studio Code Backups/Carbon Neural/2025-09-13_22-10-25/CarbonNeural_portable_2025-09-13_22-10-25/Sources/SpeccyCore'
OUT="$(mktemp -d)"
swiftc -O -parse-as-library "$SPECCY_CORE_DIR"/*.swift reverse_engineering/tools/SnapshotRoomIndex.swift -o "$OUT/SnapshotRoomIndex"
"$OUT/SnapshotRoomIndex" --self-test
"$OUT/SnapshotRoomIndex" SNAPSHOTS/Snapshot.z80 SNAPSHOTS/Snapshot_GamePlay.z80 --private-map
open reverse_engineering/private/snapshot-803e4197989c-world.html
```

The opened **private** local HTML shows 256 world positions colored by room-template ID (generic colors and numbers, not original graphics). The same private tool additionally writes a validated version-2 JSON world with all 48 room templates and measured width/height for each background to `reverse_engineering/private/snapshot-803e4197989c-world-v2.json`. The native macOS/iOS/visionOS apps can import that file into a **read-only** world explorer (see [build.md](build.md)); no original map data is bundled. Previously exported version-1 files remain importable for topology browsing, but cannot answer bounding-box queries. Both outputs and all snapshot bytes stay ignored by Git. In the captured gameplay room, a 24-by-24 background at X=32/Y=112 is consistent with the reference player stopping at X=56 when holding Q (the next leftward position overlaps its bounds). Another background at X=48/Y=40 with height 24 is consistent with E stopping at Y=87 (Y=85 overlaps while Y=86 is clear; the movement step can skip it). The measured test treats actor X as its left edge and Y as its bottom edge, including 8-bit arithmetic wraparound. The shared `WorldReference.overlapsBackgroundBounds` query and independent-axis `resolveBackgroundBounds` cover only static rectangles, without asserting dynamic actor or boundary-transition fidelity. They are not connected to the playable prototype; exact collision responses in all rooms remain unverified. This reference cross-check advances *static* map recovery; it does not establish tape revision equality or continuous input-driven behavior.

## First controlled room transition

The public, source-free [upper-exit-schedule.json](../reverse_engineering/analysis/upper-exit-schedule.json) holds W over zero-based frames 20–29 and E over frames 30–179. The private emulator replay first moves from world room ID **168** (8,10) to ID **152** (8,9) at recorded frame **68**, with player X=121/Y=42. The unmodified backup emulator independently confirmed the room ID and player X/Y for **all 180 frames**, with zero unimplemented CPU instructions. Screen-memory hashes agree for **174/180** frames; the six mismatches occur during the room redraw at frames 68–73. Differences in intermediate frame sampling are a possible cause, not yet established. Do not use the transition redraw as a pixel-exact native golden until its frame timing is reconciled. The full replay, frame hashes and original visual content remain under ignored `reverse_engineering/private/`; the viewer can scrub the private replay across the boundary.

The separate [round-trip-schedule.json](../reverse_engineering/analysis/round-trip-schedule.json) holds W on frames 20–29, E on 30–74 and R on 75–199. The player returns from room 152 to **168** at frame **88**, freezes at X=121/Y=190, then resumes at X=120/Y=39 on frame **94**. Room/X/Y match the unmodified backup emulator at **all 200 frames** with zero unimplemented instructions; screen hashes match **184/200**, with differences at frames 68–73, 88–93, 142, 155, 159 and 196. These isolated later screen differences are not assumed to be redraw timing. The shared [CapturedMovementState](../Sources/GameCore/CapturedMovementState.swift) independently reproduces room/X/Y for **all 180 north-exit frames**, **200 round-trip frames** and **600 frames of four separate 150-frame Q/W/E/R holds** using measured inertia, static background collision and bounded entry/exit delays. The launcher prepares all seven private replays. Run `SABRE_PRIVATE_WORLD=<private-world-v2.json> SABRE_PRIVATE_REPLAY=<private-replay-upper-exit-180.json> SABRE_PRIVATE_ROUND_TRIP=<private-replay-round-trip-200.json> SABRE_PRIVATE_HELD_REPLAY_DIR=<private-directory> swift test --filter CapturedMovementTests` locally for full-frame parity; public CI skips private-input tests. The app's separate pink-marker movement preview exposes this bounded slice, but does **not** implement dynamic enemies, combat, items, other exits or complete native gameplay.

### Provisional westward path

The public [west-exit-schedule.json](../reverse_engineering/analysis/west-exit-schedule.json) uses W on frames 20–29, E on 30–99, no input through frame 179, then Q on 180–255. The fresh-FE CPU reference moves from room **152** into room **151** at frame **226**, freezes for seven frames and rebases to X=239/Y=126 on frame **233**. Native static movement matches room/X/Y for all **256** frames of that private replay. **This is provisional:** the unmodified emulator's `stepFrame()` independently agrees on actor room/X/Y only through frame **182**. The chain is now bounded: a gameplay RNG byte first differs at frame **101**, just after E is released; at frame **102** a moving entity takes different X coordinates in the two replays; at frame **163** it is at X=104/Y=135 in the full emulator, close to the player at X=121/Y=126, versus X=161/Y=130 in fresh-FE CPU stepping. The full emulator changes the player into a damage state at frame **164**; when Q is pressed later, that actor initially stays stationary and subsequently follows a different route. Thus the mismatched late input is a **consequence of different dynamic-actor paths**, not evidence of a keyboard bug. The CPU refresh-register phase differs at frame boundaries, which might contribute to the RNG branch, but causation has not been established. Do not certify west-exit parity without resolving the RNG/actor timing. A longer continuous-Q probe exposes a moving-actor block at X=27 in room 152 and later in room 151. The native static-only preview deliberately omits dynamic actors instead of hard-coding pauses.

`SnapshotDivergence.swift --trace` also produces a **private** 256-frame numeric comparison of that entity slot and both player positions; the app can import it only alongside a replay whose manually stepped actor path matches every frame. The comparison renders no original sprite pixels and does not infer unobserved enemy movement rules. The entire trace remains ignored.
